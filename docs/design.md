# Устройство сервиса

`src/runtime.py` собирает зависимости и управляет жизненным циклом одного
процесса. FastAPI вызывает сервисы через SQLAlchemy async sessions.
В том же процессе работают RabbitMQ consumers `incidents.alerts` и
`incidents.projects-events`, outbox relay и dispatch worker для AI Backend.
PostgreSQL хранит бизнес-состояние и outbox/inbox. Dragonfly используется
для проверки прав и ingest-токенов; `projects` служит источником ACL и
снимков конфигурации. `auth` даёт JWKS и служебные токены.

## Конфигурация

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | SQLAlchemy async URL PostgreSQL; обязательна |
| `RABBITMQ_URL` | AMQP URL; обязательна |
| `CACHE_URL` | URL Dragonfly/Redis; обязательна |
| `AUTH_CLIENT_SECRET` | Секрет клиента `incidents` в auth; обязателен |
| `AUTH_URL` | auth, по умолчанию `http://auth.apps:8001` |
| `PROJECTS_URL` | projects, по умолчанию `http://projects.apps:8003` |
| `AI_BACKEND_URL` | AI Backend, по умолчанию `http://ai-backend.apps:8000` |
| `AUTH_CLIENT_ID` | По умолчанию `incidents` |
| `PORT`, `BIND_HOST` | По умолчанию `8006`, `0.0.0.0` |

Пул PostgreSQL ограничен тремя соединениями на процесс. RabbitMQ и
PostgreSQL нужны до запуска приложения; readiness дополнительно проверяет
PostgreSQL и Dragonfly. Outbox relay публикует события из БД после commit.

Overview считает инциденты и расследования в PostgreSQL. Фильтры
`from` и `to` ограничивают время обнаружения инцидента, а счётчик
закрытых дополнительно проверяет время закрытия за последние 24 часа.
Текущее здоровье сервисов берётся из топологии projects после проверки
`project.read`. При отсутствии фильтра окружения используются среды проекта.
HTTP-запросы выполняются до открытия сессии БД и ограничены общим таймаутом.

AI context использует то же окно, что и StartAIRequest. Сервис возвращает
только связанные с инцидентом записи из его проекта и окружения, а выкатки
дополнительно фильтрует по окну. Источник данных подключается отдельно от
чтения инцидента, после закрытия сессии БД.
Обработчики очереди используют inbox для повторных сообщений. Конкретные
exchange, routing keys и ограничения очередей задаёт
[`backend/messaging.md`](../../backend/messaging.md).

Алерт выбирает подходящее правило по приоритету из сохранённого снимка
конфигурации. Правило определяет labels для корреляции, окно эпизода и
порог автостарта. Суточная квота расследований и почасовая квота новых
инцидентов учитываются в той же транзакции, что и квитанция, инцидент,
попытка расследования и outbox.

При `Start` без достоверного ответа worker делает readback по тому же
`investigation_id`. Если пользователь затем нажал Cancel, worker сначала
уточняет admission, после подтверждения доставляет Cancel в AI. Ответ 404
на readback откладывает повторную проверку на пять секунд; после deadline
попытка закрывается локально. Очистка проекта ставит tombstone до удаления
данных и синхронизируется с приёмом новых алертов и ручным созданием.
Перед очисткой повторный `message_id` сверяется с сохранённым payload hash,
чтобы несовместимый повтор не успел удалить данные другого проекта.

## Выкатка

Job применяет `alembic upgrade head` до Deployment. Один Pod содержит все
фоновые задачи и HTTP API. При RollingUpdate некоторое время могут работать
два Pod; повторная доставка сообщений должна обрабатываться идемпотентно.
Проверки `/health` и `/ready` не доказывают доступность AI Backend, auth,
projects или здоровье RabbitMQ после старта. Наблюдаемость и нагрузочные
лимиты ещё требуют проверки в кластере.
